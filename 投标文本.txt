【详细方案】
Understanding: The buyer needs a preflight (dry-run) stage for a parsed import batch. Every row must pass through map_row -> clean -> validate -> natural_key -> upsert in that exact order, and the entire pass must execute inside one database transaction that is forcibly ROLLBACKed at the end so no business table retains a write. The only durable outputs are import_row(action, cleaned_payload, target_id) and import_issue. Update-type rows require a field-level diff listing only fields that genuinely changed. Natural keys repeated inside the same file must be flagged from the second occurrence onward with code DUPLICATE_IN_FILE and a message naming the first line number. On completion, create/update/unchanged/error/warning counts are aggregated into import_batch and its status becomes dry_run_ready when no blocking issue exists, or dry_run_failed when a blocking issue such as a missing required column is present. A deterministic fingerprint over file_sha256, mapper_version and normalized mapping_override must gate formal import: any change to those inputs forces a re-run of the dry-run.

Plan:
